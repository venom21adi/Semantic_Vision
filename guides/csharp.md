# C# support

Semantic Vision parses C# repositories into the same graph as every other
language: files, types, methods, constructors and property accessors, the
calls between them, and the `using` dependencies. Impact analysis, Code
Health (complexity, dead code, duplicates, hotspots), execution flowcharts
and AI documentation all work on it.

This page says what it understands, how well, how that was measured, and
where it stops. The accuracy numbers can be reproduced with one command.

## What it understands

C# calls are hard to attribute from text alone: `conn.Query<T>(sql)` is only
meaningful if you know what `conn` is, and `using` imports a *namespace*, not
a type. So rather than matching names, the resolver follows the same evidence
a compiler does:

- **Types, namespaces and partial classes** across the whole repository,
  including file-scoped namespaces, nested types, generic types
  (`Repo<T>` and `Repo<T, TId>` are different types) and records.
- **`.csproj` structure.** A type name resolves among the types of the file's
  own project and the projects it references, never the rest of the
  repository. Monorepos full of same-named test doubles and samples resolve
  correctly because of this.
- **Receiver types.** Locals, parameters, fields and properties by declared
  type; `var` by its initializer; `foreach`, pattern (`is Foo f`), `catch`,
  `out var` and lambda variables; method return types (`Task<T>` through
  `await`); casts, `as`, indexers, `?.`, and LINQ chains
  (`items.Where(x => x.Ok()).First().Run()` keeps its element type).
- **Overloads** by argument count, explicit type arguments and argument types,
  including `params`, optional parameters, nullable value types and numeric
  conversions; derived classes hide a base overload only when theirs applies,
  and `override` methods are treated as C# treats them.
- **Inheritance, interfaces, generic constraints** (`where T : Entity` gives
  `T` the members of `Entity`), `base(...)` / `this(...)` chaining.
- **Extension methods**, including the rule that a library type's own
  instance method always beats an extension of the same name. A table of the
  .NET framework's instance methods (`resolver/data/bcl_members.json.gz`,
  regenerated by `scripts/csharp/bcl_members`) is what makes that decidable.
- **Conditional compilation.** `#if` blocks are evaluated as a modern
  multi-target build would: `NET6_0_OR_GREATER` is defined, `NET20` is not,
  project-specific flags such as `HAVE_ASYNC` are treated as defined (so the
  code they enable is analysed). Inactive branches are not in the graph.

Calls into libraries (including NuGet packages) appear as `external::` edges;
a call whose receiver cannot be determined appears as `unresolved::` and is
flagged ambiguous. Nothing is silently guessed: when arguments cannot choose
between overloads, you get several ambiguous edges rather than one wrong one.

## How accurate is it

Measured against **Roslyn, the real C# compiler**: for every call site, Roslyn
reports the method the call binds to, and we compare.

- **Recall**: of the calls the compiler sends to a method in the repository, the
  share we attribute to that same method.
- **Precision**: of the repository methods we claim a call reaches, the share the
  compiler agrees with.

| Repository | Lines | True repo calls | Recall | Precision |
|---|---:|---:|---:|---:|
| [Dapper](https://github.com/DapperLib/Dapper) | 27 k | 2,739 | 98.9 % | 100.0 % |
| [Newtonsoft.Json](https://github.com/JamesNK/Newtonsoft.Json) | 197 k | 24,598 | 98.8 % | 99.5 % |
| [Jellyfin](https://github.com/jellyfin/jellyfin) † | 365 k | 19,725 | 98.0 % | 98.2 % |
| [EF Core](https://github.com/dotnet/efcore) † | 1.8 M | 240,237 | 89.1 % | 96.8 % |

† **Held out**: never used while building the resolver, so these show how it
does on code it was not tuned for. Dapper and Newtonsoft.Json were used for
development and are best read as the ceiling.

Pinned commits: Dapper `eb47546` · Newtonsoft.Json `52fa3ae` · Jellyfin
`df62c85` · EF Core `bf13836` (2026-09 to 2026-11 snapshots).

Typical application code lands near 98 %. EF Core is the hard case, and its
89 % is explained by patterns that need real type inference:

- generic test base classes (`TestBase<TFixture>` where the fixture type
  decides which context is returned),
- target-typed `new()` (the type comes from the assignment, not the call),
- generic method type inference without explicit arguments,
- a derived class that narrows an inherited member's type, so the call lands on the
  more specific type's method.

Calls that depend on NuGet packages the compiler was not given cannot be
bound by Roslyn either, so they are excluded from the comparison and shown
as `external::`/`unresolved::` in the graph.

### Reproduce it

You need the .NET SDK (the comparison itself is pure Python):

```bash
git clone --depth 1 https://github.com/DapperLib/Dapper.git
uv run python scripts/csharp/validate.py Dapper            # prints recall / precision
uv run python scripts/csharp/validate.py Dapper --show 5   # plus examples of every miss
```

The repository's own fixture is checked against the compiler in the test
suite: `SV_CSHARP_ORACLE=1 uv run pytest tests/test_csharp_oracle.py`.

## How fast is it

Parsing and resolving a repository, one machine (12 cores, Windows 11), cold
cache:

| Repository | Files | Lines | Parse + resolve | Peak memory | Code Health index |
|---|---:|---:|---:|---:|---:|
| Dapper | 157 | 27 k | 1.4 s | 70 MB | 0.9 s |
| Newtonsoft.Json | 951 | 197 k | 7.4 s | 170 MB | 4.7 s |
| Jellyfin | 2,252 | 365 k | 15 s | 270 MB | 8 s |
| EF Core | 5,872 | 1.8 M | 90 s | 1.3 GB | 53 s |

The Code Health index (complexity, hotspots, duplicates) is computed once on
first use and cached. Memory is dominated by the call-site records, roughly
0.7 KB per source line.

## Limits

- **No runtime knowledge.** Dependency-injection wiring, reflection,
  `dynamic`, source generators (their output is not on disk) and
  configuration-driven dispatch are invisible. A call through an interface
  points at the interface method, not at implementations.
- **Property reads are not calls.** A property accessor with logic is a node,
  but reading `order.Total` does not draw an edge to it; accessors are marked
  as framework-invoked so they are not reported as dead code.
- **Conditional compilation picks one configuration.** Code that exists only
  in an inactive `#if` branch (another target framework's variant) is not
  analysed.
- **Syntax the grammar mishandles.** A few constructs (for example assigning
  to a ref-returning call, `X() = value`) are not understood by the C# grammar
  we use; the affected calls are missed, the rest of the file is kept.
  `async` used as an *identifier* is worked around.
- **Not supported yet:** Razor / Blazor (`.cshtml`, `.razor`), C# script
  (`.csx`), F# and Visual Basic, NuGet package reading for the Dependencies
  tab (`.csproj` is read only for project references).
